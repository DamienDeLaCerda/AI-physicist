The advisor’s guide to an AI physicist.

Get Physics Done installs a research workflow into the coding agent you already run. It carries a question through scope, derivation, numerical checks, and a manuscript. You remain the person who can defend every claim.

01Stay in the advisor’s chair

The system is built for a long physics project: multi-step analysis, numerical studies, a memory that survives the chat, and a manuscript at the end. It is built to prefer a checkable claim over an agreeable one.

Treat each agent turn like a graduate student’s work: trust the execution, but stay in the loop to verify and redirect. Get Physics Done, on supervised mode

Supervised mode is the matching posture. It stops often enough that you can redirect a convention, a sign, or a numerical cutoff while the work is still cheap to redo. Balanced mode comes later, after you have seen how the system behaves on your problem.

A preferred explanation is a hypothesis. A failed lookup stays failed. An artifact that was never produced stays absent. Those three habits are the difference between a collaborator and a fluent draft.

02Who does what

Send this page to the group before the first working session. The roles below are the ones that keep a result publishable.

Principal investigator

You set the question, the autonomy, and the claims allowed into the paper. Read the verification for a phase before you accept the milestone. Start on Supervised.

Postdoc or student

You run one phase at a time. Bring your advisor the verification file and the state note, and keep the roadmap honest about what is still a stub.

Research engineer

You own Node.js 20+, Python 3.11 with venv, the runtime login, and LaTeX when a paper is in scope. Pin a release for the group. --upgrade tracks unreleased main.

03The record is the project

Chat is ephemeral. The durable memory is a folder named GPD/ inside the research directory. Opening that folder should tell a colleague where the work stands without scrolling a transcript.

A phase is one coherent chunk of the milestone. Integer phases are the planned work. A decimal such as 2.1 is urgent work inserted later. Early phases beyond the one you are executing often remain stubs until someone runs plan-phase on them.

Each phase is expected to leave real files: PROJECT.md, REQUIREMENTS.md, ROADMAP.md, STATE.md, TeX derivations, Python checks, and figures. Across a long project the system can lock notation, sign choices, and verification assumptions for as many as 18 physics fields, so later phases inherit the same conventions.

Before you step away. Run pause-work so the handoff is explicit. On return, gpd resume in a normal terminal reads the current workspace. If that is the wrong folder, gpd resume --recent lists others. Inside the runtime, resume-work continues, and suggest-next is the fastest following command.

04The working loop

Install once from a normal terminal, in the folder where the project should live. The research commands then run inside the agent, with a prefix that depends on the runtime.

npx -y get-physics-done

Node.js 20 or newer, Python 3.11+ with venv, and one runtime already installed: claude, codex, gemini, gh copilot, or opencode. On Windows, winget install OpenJS.NodeJS.LTS provides node and npx. To pin a runtime to this folder, pass the flags after --, for example npx -y get-physics-done -- --claude --local. Swap --claude for --codex, --gemini, --copilot, or --opencode.

After install, both of these should succeed: gpd --help in the normal terminal, and the runtime’s help command in the agent. gpd doctor is the readiness check. A warning that only mentions workflow presets or the LaTeX toolchain means the base install is usable and the manuscript tools are the part still thin. gpd paper-build is the build truth for a paper.

start is for a folder whose path you have not chosen. tour is a read-only walkthrough. new-project --minimal opens new work. map-research adopts a folder that already has notes or code. Pick one of those two and stay with it.

One phase, then the next

discuss-phase 1→ plan-phase 1→ execute-phase 1→ verify-work 1

The full research loop is new-project, then that phase sequence, repeated, then complete-milestone. progress reports where the roadmap stands. gpd progress --watch in a second terminal is a live heartbeat. gpd observe execution is the read-only status when a long run goes quiet; if the status is uncertain, treat it as possibly stalled and inspect gpd observe show --last 20.

A side idea goes through tangent first: stay on the main line, take a short detour, defer it, or escalate. branch-hypothesis is the git-backed alternative, and compare-branches puts those results side by side. Use the branch when you mean to keep both lines.

05A worked research path

The upstream project’s own example is a numerical conformal bootstrap for the 3D Ising CFT: bound low-lying operator dimensions from crossing symmetry. Inside the runtime, after the prefix for your agent:

new-project
Use crossing symmetry and the numerical conformal bootstrap
to bound low-lying operator dimensions in the 3D Ising CFT.

Formulation should ask about the correlator sector, conventions, target observables, numerical precision, and the verification strategy. It should then write GPD/PROJECT.md, REQUIREMENTS.md, ROADMAP.md, and STATE.md.

A sensible milestone sketch, which you flesh out one phase at a time, looks like this:

  1. Crossing-equation setup
  2. Derivative-basis construction
  3. Semidefinite-program formulation
  4. Convergence checks
  5. Interpretation of the bounds

Phase 1 is the one ready to execute. The rest stay stubs until you call plan-phase on them. Then:

plan-phase 1
execute-phase 1
verify-work 1

Expect derivation notes, numerical scripts, convergence studies, and a verification document under GPD/. When the phases that carry the result are verified, the publication path is write-paper, peer-review, respond-to-referees, arxiv-submission.

06What to demand before you believe a phase

Verification is the stage that makes this a physics workflow. Read it the way you would read a student’s calculation before it goes into a draft.

  • 01Dimensional consistency of every displayed relation.
  • 02A limiting case you already know: a free theory, a static limit, a recovered textbook formula.
  • 03The symmetry or conservation law the result is required to obey.
  • 04Numerical stability where a number will be quoted: cutoff, grid, seed, convergence.
  • 05An explicit record of missing evidence. A lookup that failed is part of the result.

Single-shot analysis can also be run from the current workspace, with outputs under GPD/analysis/: derive-equation, dimensional-analysis, limiting-cases, numerical-convergence, and sensitivity-analysis. A parameter sweep needs an explicit script plus --param and --range, and it writes under GPD/sweeps/.

Calibrate on a known result first. Point the first project at a derivation your group can redo by hand — a harmonic oscillator ladder, a cross section you teach, a limit of a formula already in your notes. Accept the workflow only after verify-work agrees with that standard. Then aim it at the open problem.

07Choose a posture, then leave the defaults alone

The safest model-cost start named by the project is the review profile together with the runtime’s own default models. Change tiers only when you have a reason: consistency at the top end, or a tighter budget.

deep-theory

Long analytic arguments, convention-heavy calculation, careful notation.

numerical

Solvers, sweeps, convergence, and the scripts a referee might rerun.

exploratory

Early scoping, when the question is still moving and stubs are expected.

review

The conservative default. Use it while you learn the system’s boundary.

paper-writing

Manuscript assembly after the verified phases exist.

Profiles are set inside the runtime: /gpd:set-profile review on Claude Code and Gemini CLI, $gpd-set-profile review on Codex, and /gpd-set-profile review on Copilot CLI and OpenCode. settings on the same prefix is where autonomy, workflow defaults, and permission sync live. Keep autonomy at supervised until the checkpoints feel right, then consider balanced.

Three capability tiers exist if you later pin models: tier-1 highest, tier-2 the middle, tier-3 the fastest. Model strings are whatever that runtime already accepts. gpd cost reads local telemetry and is an advisory view of spend, separate from the provider’s bill.

08From a verified phase to arXiv

write-paper→ peer-review→ respond-to-referees→ arxiv-submission

write-paper drafts from the current project. It can also take one explicit intake manifest (write-paper --intake …) for a bounded external manuscript. In that lane the manuscript root is GPD/publication/<subject>/manuscript, and the intake folder holds provenance. The tool does not harvest an arbitrary directory of notes and invent which claim has evidence.

peer-review reads the project manuscript, or one path you name. respond-to-referees stays on the resolved manuscript. arxiv-submission packages a GPD-owned manuscript root or a .tex entrypoint. It is the packaging step, and you still submit.

If LaTeX is part of the plan, run gpd doctor and read the workflow-preset and LaTeX rows before you promise a camera-ready PDF. Optional local probes (--live-executable-probes) include pdflatex and, where you use it, wolframscript. Shared Wolfram status is gpd integrations status wolfram.

09An afternoon to the first checkpoint

  1. Install Node.js 20+ and confirm python --version is 3.11 or newer and that python -m venv works.
  2. Confirm one runtime launches and is signed in: claude, codex, gemini, gh copilot, or opencode. The installer does not create that account or supply model credit.
  3. In an empty project folder, run npx -y get-physics-done. Add -- --claude --local (or another runtime flag) when you want the scope explicit.
  4. Run gpd --help and gpd doctor. Fix Node, Python, or the runtime launcher before you debug the physics commands.
  5. Open the runtime. Run its help command, then tour if you want the map, then new-project --minimal on a result the group already knows.
  6. Run discuss-phase 1, plan-phase 1, execute-phase 1, and verify-work 1. Prefix them the way the table in the loop section shows.
  7. Open GPD/STATE.md and the verification file yourself. Compare the limiting case with the known result.
  8. Only then point a new project at the question you cannot yet answer. Leave autonomy on Supervised.

The full command reference inside the agent is help --all with your runtime’s prefix (/gpd:help --all, $gpd-help --all, or /gpd-help --all). This page is the orientation; that help text is the manual.

10Your name stays on the paper

  • You choose the question, the conventions, and which numerical error is small enough to publish.
  • You read the verification artifact. A fluent derivation with no limiting case is still unfinished.
  • You check citations. Literature commands such as literature-review and digest-knowledge are assistants to that reading.
  • You answer the referee. respond-to-referees can draft against the manuscript root; the letter that goes back is yours.
  • You decide when a tangent becomes a second hypothesis branch worth the group’s time.
  • If the system contributed to a published result, cite it. The block below matches the upstream README for version 1.2.2. Prefer CITATION.cff in the repository you actually ran.
